# Security Agent — Аудит v1.95.4

**Исполнитель:** Алексей Смирнов (Cybersecurity Engineer)
**Дата:** 2026-05-08
**Цель:** Аудит безопасности проекта `translateVideo` версии 1.95.4.

## Общий вывод

Проект демонстрирует хороший базовый уровень безопасности: используются переменные окружения для секретов, есть HMAC-подпись для вебхуков, внедрены security-заголовки (OWASP), используется линтер и аудит зависимостей.

Тем не менее, выявлен ряд уязвимостей и рисков, требующих внимания. Основные векторы атаки: эксплуатация Docker-конфигурации, некорректная конфигурация в production и уязвимости в зависимостях для обработки медиафайлов.

## Найденные уязвимости и риски (10)

| ID | Категория | Описание замечания | Риск | Рекомендация |
|:---|:---|:---|:---|:---|
| **S-1** | **Контейнеризация** | **Запуск контейнера от имени root-пользователя.** `Dockerfile` не содержит инструкций `USER` для переключения на непривилегированного пользователя. В случае компрометации приложения злоумышленник получит root-доступ внутри контейнера. | **Высокий** | В `Dockerfile` добавить создание non-root пользователя и переключиться на него через `USER appuser`. |
| **S-2** | **Конфигурация API** | **Риск небезопасной CORS-политики в production.** Код в `api/main.py` позволяет установить `ALLOWED_ORIGINS=*`. Ошибочная конфигурация в production откроет API для любых сайтов, что чревато CSRF-атаками. | **Высокий** | Вместо `*` использовать явный и закрытый список доверенных доменов в production-окружении. Добавить валидацию переменной `ALLOWED_ORIGINS`. |
| **S-3** | **Аутентификация** | **Использование единого общего API-ключа.** Система `APIKeyMiddleware` использует один ключ для всех клиентов. Это затрудняет ротацию ключей и идентификацию конкретного клиента в логах. При компрометации ключа все интеграции оказываются под угрозой. | **Средний** | Внедрить механизм множественных API-ключей (например, `API_KEYS` со списком). В идеале — перейти на JWT или OAuth2 для гранулярного контроля доступа. |
| **S-4** | **Конфигурация API** | **Чрезмерно подробный health-check endpoint.** Endpoint `/api/health` раскрывает много служебной информации (пути, версии, retry-конфиги, количество запущенных проектов). Это помогает злоумышленнику в профилировании системы. | **Средний** | Разделить endpoint на public (`/api/health/status` с `{"status": "ok"}`) и private (`/api/admin/health` для аутентифицированных администраторов с полной информацией). |
| **S-5** | **Обработка данных** | **Риск Command Injection через `yt-dlp`.** Команда `download` в `cli.py` принимает аргумент `--format`, который напрямую передаётся в `yt-dlp`. Специально сформированная строка формата потенциально может привести к выполнению произвольных команд. | **Средний** | Валидировать значение аргумента `--format` по белому списку разрешённых и безопасных форматов. |
| **S-6** | **Конфигурация окружения** | **Противоречивые настройки окружения.** `Dockerfile` устанавливает `APP_ENV=production`, но `cli.py` запускает `uvicorn` с `reload=True`. Это может привести к активации debug-режима в production и утечке стектрейсов при ошибках. | **Средний** | Убрать `reload=True` из `_handle_server` в `cli.py`. Управлять режимом запуска через переменную окружения, а не хардкодить его. |
| **S-7** | **Контроль доступа** | **Риск утечки данных через статическую раздачу `/runs`.** В `api/main.py` есть логика, позволяющая включить статическую раздачу всей директории `/runs` через `EXPOSE_RUNS_STATIC`. Случайная активация этой опции в production откроет доступ ко всем видео и артефактам. | **Высокий** | Удалить эту функциональность. Для доступа к артефактам использовать только защищенные эндпоинты API с проверкой авторизации. |
| **S-8** | **DoS** | **Отсутствие ограничения на размер загружаемого файла.** API-эндпоинты, принимающие видео, по-видимому, не имеют явного ограничения на максимальный размер файла. Это создаёт вектор для DoS-атаки через исчерпание дискового пространства или памяти. | **Средний** | Внедрить ограничение на максимальный размер загружаемого файла в FastAPI (например, через `request.headers['content-length']` и middleware). |
| **S-9** | **Supply Chain** | **Риски в библиотеках обработки медиа.** Проект использует `moviepy`, `ffmpeg`, `faster_whisper` для обработки ненадёжных данных (видеофайлов). Уязвимости в этих библиотеках могут привести к RCE или DoS. `pip audit` не покрывает нативные зависимости типа `ffmpeg`. | **Низкий** | Регулярно обновлять все зависимости, включая системные (`ffmpeg`). Изолировать обработку медиа в отдельных, максимально урезанных контейнерах. |
| **S-10**| **Сетевая безопасность**| **Использование `urllib.request` в вебхуках.** Модуль `webhook.py` использует стандартную библиотеку `urllib` для отправки POST-запросов. Эта библиотека менее надёжна и безопасна по сравнению с `httpx` (уже есть в проекте) в части обработки TLS, таймаутов и редиректов. | **Низкий**| Заменить `urllib.request` на `httpx.Client` для отправки вебхуков, чтобы унифицировать сетевой стек и повысить его надёжность. |
